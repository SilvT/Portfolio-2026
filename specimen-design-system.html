№01 — The published styleguide: tokens, documented and browsable.

№02 — One component, every state: size, hierarchy, hover, focus, pressed, disabled.

This system was built with no formal approval, no precedent, and no one at the company who yet believed design systems counted as infrastructure — so it was built anyway, as a proof of concept smuggled inside a live CRM dashboard project, on the principle that it's easier to ask forgiveness than permission. A three-level token architecture (primitive → semantic → component) and a custom Figma-to-GitHub pipeline turned a slow, manual, error-prone hand-off into a shipped, versioned artefact an engineer-first CEO could actually see the value of. He did: within six months this became a promotion to Design Systems Lead, and the system scaled from one product to an audit of all seven.

Zooming In: Tokens to Shippable Code

Tokens lived in Figma; the developer in Japan needed them as consumable JSON. A custom Git Action paired with a Figma plugin closed that gap — exporting primitive, semantic and component tokens straight from Figma into the codebase, with every export timestamped and change-counted automatically.

№03 — Full pipeline: plugin export → alpha ramps → phased rollout plan, core through component level.

Context: What It Replaced

№04 — The previous process: styles and components, manually reconciled against code.

No Shared Source of Truth

Before this, three product lines had each accumulated their own disconnected UX, playground and UI files — no naming conventions, no shared libraries, hand-off pages manually kept in sync with the code repo by whoever had time.

№05 — The testbed: an early build of the Marketing Management CRM, net-new to the company.

Built Inside a Live Product

Rather than pitch a system no one had asked for, the token architecture was proven on a real product first — a marketing CRM dashboard, designed solo opposite a backend developer and a frontend developer seven time zones away.

Strengths

№06 — States as modes, not as a multiplied component count.

Variable Modes Instead of Variant Sprawl

Interactive states (hover, press, focus, disabled) and on/off statuses were modelled as Figma variable modes rather than duplicated as separate component variants — cutting redundant token naming and keeping components genuinely composable instead of bloated.

№07 — One export, fully accounted for: timestamp, change count, token breakdown.

A Pipeline, Not a Hand-off Ritual

The custom Git Action plus Figma plugin turned token hand-off from a manual, error-prone chore into a one-click export — a side effect of which was unlocking white-label capability for an unrelated earlier product, which is what first got the CEO's attention.

№09 — The scaffolding that outlived one product: a repeatable three-phase rollout.

Governance That Could Scale

After CEO buy-in, the same phased model — tokens, styles, components, documented in that order — became the basis for auditing all seven product lines and training an expanded eight-person design team across eight or nine workshops.

Quirks

№10 — Alert tokens, filed as Core when they were really Semantic.

Naming Discipline, Learned Mid-flight

Alert and graph values were initially filed under the Core collection despite being semantic rather than primitive — caught and annotated during a later audit pass, not before. The three-level architecture was correct; getting every token into the right level the first time wasn't automatic.

№11 — Gradients raised the same question twice: not core, not quite semantic either.

No Dark Mode, by Trade-off

Using variable modes for interactive states — rather than a more generic token structure — made the system harder to extend to light/dark theming later. Not a requirement at the time, so the right call for the problem in front of it, but a cost that would resurface if theming became a requirement.

№12 — One designer, one system, one product, for most of its working life.

Documentation, Deferred on Purpose

No traditional component documentation existed for most of the build — a deliberate trade-off while the sole consumer of the system was its own author. It held up, but it also meant the system lived in one person's head for longer than was comfortable once the team started to grow.

№13 — Scaling across seven product lines, before the company could finish scaling with it.

The Scaffolding Outlived the Company

Guidelines, a Confluence governance template, and a planned dedicated governance role were all built out — but Senapt went bankrupt before the progressive scaling model reached full execution. The structure existed; the runway to finish it didn't.
