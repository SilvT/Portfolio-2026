Design infrastructure built solo, with no precedent, inside an engineer-first startup.

No file naming conventions, no shared libraries, no design structure, and no one at the company who yet believed a design system counted as infrastructure.

I joined Senapt as its second full designer, and was handed their fourth product line: a Marketing Management Desktop App, a campaigns,leads and channels dashboard. Designed solo opposite a backend developer and a frontend developer seven time zones away in Japan, who read written English but wasn't a fluent speaker and asked to be spared video calls entirely. Handing off ambiguous screens across that gap meant every misunderstanding became a delay; across the other product lines, designs were taking four or five review rounds after handoff, and developers sometimes shipped straight to a live product without design sign-off, with corrections happening after the fact. My purpose was to build this product component-first and heavily annotated from day one, to close that gap before it opened.

This design system was product specific, yet aimed at the whole company; proven first as a proof of concept inside that one desktop app, because asking forgiveness was faster than waiting for a permission nobody was ready to give. The first formal pitch to the CEO was turned down outright.
The VP of FE gave a tentative yes, though not for reasons I loved (he saw a system as a way to let FE bypass designers on some work).
My own response at the time: "Not ideal, we don't want designers to be bypassed, but we'll take the support for now as a starting point."

Context: The First Drafts

№01 A rough first layer of values was laid out to have something to work on top of.

No buy-in? Lead by example

Three already existing product lines, each built by freelancers with no engineering mindset behind them, had accumulated their own disconnected UX, playground and UI files: no naming conventions, no shared libraries, hand-off pages manually kept in sync with the code repo by whoever had time that sprint. After turning down my system-approach pitch, the token architecture was proven on a real product first, built alongside the Marketing Management Desktop App rather than keep pushing for approval without concrete evidences.

Scaffolded in Phases, building on the go

I was juggling with product key features desicions, research, ux flows, ui and handoffs. The system was never going to land in one pass, nor be sturdy from the begining, so it didn't try to. Phase 1 proved the core: tokens, type, a first handful of components, enough to ship the dashboard's earliest screens. Phase 2 expanded it: semantic tokens, gradients and elevations, a wider component set drawn from what the product actually needed next. Phase 3 pushed into cards, sections and slots, with documentation status tracked against each prior phase rather than assumed complete.

Delivery order was components first, screens second, every time. Changes cascaded predictably because the architecture underneath them was correct from phase one; it didn't need revisiting, only extending.

The semantic layer was wrong twice, in two different ways. The first pass was thin, loosely drawn from an outside reference I no longer remember, and token creation quickly skipped past it: component tokens piled up connected straight to primitives, card by card, with no real hierarchy underneath them. There was no dedicated time to build the system properly either; shipping UI and building the token architecture were happening at once, with zero UI to start from. About five to six months in, once a full user flow existed to look at (login through to a first working set of screens), the pattern was obvious: this was going to become unmanageable. I gave my frontend developer a heads-up that a bigger structural change was coming, then deleted the original semantic layer and rebuilt it from what the screens were actually using.

That rebuilt layer held for a while, but around month ten to twelve, a different problem showed up: patterns that repeated across many components, like text keeping the same hover, focus and disabled behaviour everywhere it appeared, or a card background behaving consistently regardless of where it was nested, which weren't semantic in the usual sense but weren't component-specific either. Forcing them into semantic made semantic unstable again, and a full rebuild didn't make sense for the time or resources available. I looked for a precedent in other design systems and found none, so I added a fourth level between semantic and component, post-semantic, to hold exactly that kind of cross-component pattern. Mode usage inside it stayed deliberately narrow: no Figma variable modes, just named values (text-hover, text-focus, text-disabled), because using modes there would have meant splitting post-semantic into several collections instead of one, working against keeping the system slim enough for one person, moving fast, to maintain alone.

Token delivery had a false start too. My first proposal was to push tokens via Token Studio to Git as JSON; the VP of FE denied it outright: "why JSON? that's not a useful file format for us", with no alternative suggested. The second proposal, direct repo access with me pushing from my own machine, was approved, though it still meant manually copying and cleaning CSS output by hand for a stretch. The eventual pipeline wasn't solo work either: I reached out to a fullstack developer elsewhere in the company, not on my project, to help scope the GitHub Action properly.

In a regular meeting I walked him through the handoff method: component annotations covering styling specifics, element behaviour (on hover X, on click Y), data origin or meaning, and flagged future work; hand-delivered tokens; screen recordings; screen-grabs with arrows drawn on them; and a "Ready to Dev" and "Mark as completed" status pair, set by me and by him respectively, so handoff state stayed legible across the time difference without a live call. He was impressed enough that it changed how the rest of the work was received. When he later saw the Git automation specifically, the reaction was immediate: "CEO validates DESIGN SYSTEMS!!!!" He asked to implement the approach across every other project.

Zooming In: Tokens to Shippable Code

Tokens lived in Figma; the developer in Japan needed them as consumable JSON. Getting there took two attempts: the first proposal, pushing tokens via Token Studio to Git as JSON, was denied outright by the VP of FE, with no alternative suggested. The second, direct repo access with tokens pushed from my own machine, was approved, though it still meant manually copying and cleaning CSS output by hand for a stretch, and scoping the eventual GitHub Action properly took help from a fullstack developer elsewhere in the company. What came out the other end was a custom Git Action paired with a Figma plugin, exporting primitive, semantic and component tokens straight from Figma into the codebase, with every export timestamped and change-counted automatically.

Strengths

№04 ~50% faster hand-off, a mature CRM dashboard built entirely from the system

№05 A pipeline, not a hand-off ritual

~50% Faster Hand-off

Component-first delivery, build the pieces, annotate every state and edge case, assemble screens second, cut hand-off time by roughly half compared to other teams at the company, by informal comparison with other designers rather than controlled measurement. Set against the baseline it replaced: four or five review rounds per handoff, sometimes corrections happening after a product had already gone live.

A Pipeline, Not a Hand-off Ritual

The side effect mattered as much as the fix: the same pipeline that turned token hand-off into a one-click export also unlocked white-label capability for an unrelated, earlier product, which is what first got the CEO's attention, independently of the design system pitch itself. Within roughly five to six months, that became a promotion to Design Systems Lead.

№06 Governance that could scale

Governance That Could Scale

Once the company committed, the real scale came into view: 7 product lines running on 6 different dev stacks (React, Flutter, Vue, Nuxt, JS, JavaFX), only one of which had any token pipeline at all. Three structural approaches were weighed by name, one design system per project, a headless design system, or a hybrid global system, with clear rules set for what could move without sign-off: core tokens frozen unless discussed directly with me, semantic tokens editable with discussion and mandatory documentation, project-specific token types allowed by request.

The library's own analytics backed that scale up with real numbers: 238 components and 451 variables, inserted by three teams over the year. Senapt's own design team accounted for most of it, but the Tomato Design Team, building the Energy Switching Tracker on a separate product line entirely, was in there too, proof the token pipeline held up outside the product it was built for.

The approach to scaling the team was "education, not imposition": fill the knowledge gap first, then implement and follow through on rules and guidelines. I was still doing UI/UX/product work on my own project at the same time, so a direct-control model wasn't realistic; a small team of seven made a collaborative, workshop-led model workable instead.

That took the form of a five-part internal series, Design Bites: the 1.01 sessions, covering foundations, components and terminology, governance, design tokens, and naming systems, alongside hands-on workshops: brand and component self-audits, a shared design-principles exercise, an expert walkthrough on tokens, and first-iteration attempts at the company's own core and semantic tokens.

Reception was outstanding: changed behaviour across every team member but one, followed by individual conversations and requests from designers wanting to work out how the theory applied to their own product's daily reality.

Quirks

№07 Naming discipline, learned mid-flight

Naming Discipline, Learned Mid-flight

Alert and graph values were initially filed under the Core collection despite being semantic rather than primitive, caught and annotated during a later audit pass, not before. It wasn't an isolated slip either: the first semantic-token pass had the same root problem elsewhere, cards, titles and body text filed at the same level as backgrounds and strokes, no clear hierarchy, a novice error of jumping to component level before the semantics were properly worked out. The three-level architecture itself was correct throughout; getting every token into the right level the first time wasn't automatic.

№08 No dark mode, never a requirement; single-mode by design across core, semantic, post-semantic and component

№09 Documentation, deferred on purpose, while the system's only consumer was its own author

No Dark Mode, Never a Requirement

Dark mode wasn't a requirement or a concern at any point; it was kept out of MVP scope from the beginning. Figma's variable modes were used narrowly even where they were used at all: a small number of isolated collections, scoped to the component layer, for statuses, alert types and on/off. Core, semantic, post-semantic and component were all kept single-mode on purpose, to avoid multiplying collections for every interactive state. That choice kept the system contained and fast to work in alone, but it also means a theming requirement later would mean restructuring those collections rather than just adding a mode.

Documentation, Deferred on Purpose

No traditional component documentation existed for most of the build, a deliberate trade-off while the sole consumer of the system was its own author. It held up, but it also meant the system lived in one person's head for longer than was comfortable once the team started to grow, eventually scaling to 8 designers. That gap is part of what the later Design Bites series was built to close: five internal sessions and hands-on workshops, run once governance work began, rather than documentation written as the system was built. With earlier buy-in, component documentation would have started sooner, even lightweight, instead of waiting for a workshop series to catch up.

Learnings

The architectural call to add a fourth level rather than force those patterns into semantic, or rebuild the whole system to accommodate them, was the right one for the problem it solved; it stayed the right call even in hindsight. What I'd revisit is sequencing: with earlier buy-in, component documentation would have started sooner, even lightweight, instead of living in one person's head for the length of the build.

The governance model was still being tested when the company went bankrupt, before the scaling model reached full execution. The structure existed, and the reception from the team it was tested on was genuinely strong; the runway to prove it at full scale didn't.
