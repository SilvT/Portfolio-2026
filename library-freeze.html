A process and a plugin: a full system to provide stability to a 4-library design system with multiple designers.

Eight designers, four library files, and no record of what changed between one sprint and the next.

I joined this multi-brand design system about six months into the project, brought in as Senior Design System Strategist via Nateevo. The foundation was already in place (variables, a commons/brand split, half the first component batch built), yet with up to 8 designers working on the libraries at the same time there was no process for tracking ownership of changes across sprints. Developers needed to know what had shifted before pulling an update and who to ask for clarifications; designers needed to tell each other what they'd touched. In practice, that happened in Teams messages and meetings, and got lost the moment the library grew past a certain size. Inspired by the developing team's code freezes per sprint, I built the process and the tooling to fix that: a Figma freeze cycle and a generative Figma plugin that logs, compiles and summarises changes as they happen.

Context

--context-diagram- the 4-library structure holding around 3K components

The Starting point: 3000 components but no tracing.

Four levels, variables shared across brands, a commons layer, an extended commons for retail brands, and (at that point) two brand-specific UI kits: Brand A, web-first, and Brand B, app-first. Together holding around 3000 components counting variants individually and 8 designers working across them daily, pulled in from several different consulting companies, most with no prior design systems experience and no clear hierarchy despite a nominal lead. Separately, the dev team pulled from these libraries on 2-week sprints that mirrored the design cycle. The problem wasn't the size of the libraries. It was that, between each sprint, there was no record of what had changed or who changed it, and the bigger the libraries grew, the worse that got.

Before building anything we needed to set a process, not just a tool: a library freeze aligned to the dev team's sprint. At the end of each sprint, design freezes the library at a known state; development pulls from that save point. It gave both teams a shared clock; everyone knew which version they were aligned to, and a changed library stopped being something developers discovered mid-sprint. The plugin came after the process, not instead of it, to make that freeze cheap to run and easy to trust, rather than another manual step someone would eventually skip.

Security policies within the Client's Figma environment required all plugins to be requested via a formal acceptance process. Any new plugin needed admin approval before the test cycle, and that timeline ran longer than it would've taken me to just build a custom one myself.
So I did.
Not to bypass process for its own sake, but because the team needed the tool before the request cycle would have delivered it.

It started as a page of rules. Freeze on day 7, starts at noon, etc etc. Six rounds in, the process became clearer on each one landing on the current updated structure: 5 defined stages, a streamline process, clear ownerships, roles and outcomes criteria. Documentation was updated and readied for future potential onboardings on the team, separating each phase with its own checklist and support templates and prompts.

Clear rules and red lines were set for the team: Foundations must be left untouched once a freeze starts; anything that comes up gets queued for the next sprint instead.
Benefit from having a larger design systems team, the role of conductor of the freeze rotates, with this sprint's conductor becoming next sprint's reviewer, so the process doesn't depend on one person remembering how it works.

Underneath it all: The need for a Tool.

With a system now in place a hidden friction point came clearer into view. We were relying on what was pending to be published on each library as the only, very unreliable source of changes across the libraries. I devised a POC changelog using a Notes component from our toolkit, to be used and left by designers next to the components touched, iterated or created, so they could all be collected by the time the freeze came around.

This became the foundation and defined the PRD of the Changelog Plugin.

The Plugin: Functionalities

Add entry

Logged by designers as they work. Click a component, the plugin pre-fills name, user, timestamp; you add the note. Colour-coded by change type. No context switching, nothing to remember later.

General and Partial Changelog

Collected at the end of each sprint on its own dedicated page.

Freeze

Run once per sprint, by the lead. Compiles every scattered partial entry into one changelog, creates a named save point in Figma's version history, and feeds the compiled log to an LLM to generate a plain-language publish summary for developers.

Snapshot

A JSON snapshot of every variable value at freeze time. Each new freeze diffs against the last, auto-detecting token changes instead of anyone hunting for them.

Diff

View the list of differences on a downloadable file.

Plugin in use

1/3

Real time usage examples and displays of plugin and its functions.

The friction was deliberately kept as low as possible. We are asking for designers to keep in mind and remember they have to log the changes right after they are done.
Key decisions to achieve this:

  • Figma Generative plugin instead of traditional plugin: an unexected benefit of figma's own generative plugins is that they are bound to the files they are run in AND they appear on the right action bar. No need to remember to launch a plugin, it's always there on hand ready to use it.
  • Auto detect and auto fill: component's name is filled by simply selecting the component on the canvas. User name and timestamp are autogenerated - removing the ownership traceability problems.
  • Daily use first an upfront: plugin opens ready to log in a partial log. No navigation inside needed. Freeze and Snapshop functions are a couple clicks away, with a double verification built in to avoid unwated overwrites or untimely compilations.

The Partial Changelog entry tab in particular needed almost no explanation; the lower the friction to log a change in the moment, the more likely anyone actually does it.


Outcomes

Full adoption of the process and plugin within the first two months.
Freeze documentation and steps ready for onboarding.
Across 4 successful full freeze runs, plugin performs with no bugs detected, zero pushback. Plugin is now self-published on Figma Community.

Learnings

Honestly, not much went wrong here, and that's worth saying plainly rather than inventing a struggle to sound reflective. The team wanted structure, the process held up sprint after sprint, the plugin didn't need a single bug fix. That's rare enough that I don't want to manufacture a lesson where there wasn't a real one.

If I'm pushing for something genuine: the system was never tested against a third brand joining the commons library, so we proved it works at the scale I actually ran it at, not necessarily beyond that. And the plugin fixes the friction of logging a change, but not the moment someone simply moves on without logging it at all; that's a timing gap, not a UX one.

Now that it's available on Figma Community, being used outside the one environment it was built around, I'm looking forward to see whatever bugs or edge cases that may surface in various environments and scales.
